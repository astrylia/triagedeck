# ADR 0002：在 Service 层显式校验成员关系来隔离租户

- 状态：已采纳
- 日期：2026-10-08

## 背景

一个用户可以属于多个组织（租户），在不同组织里角色不同（OWNER / ADMIN / AGENT / CUSTOMER）。所有组织内的数据都必须只对该组织的成员可见。计划里最初写的是 `@PreAuthorize` + 请求级 `TenantContext`。

## 决策

1. 组织 id 放在 URL 路径里：`/api/orgs/{orgId}/...`。JWT 只带用户 id，不带组织和角色。
2. 每个组织下的 Service 方法，第一步显式调用：
   - `MembershipService.requireMembership(userId, orgId)`：只要求是成员；
   - `MembershipService.requireRole(userId, orgId, roles...)`：还要求角色在允许范围内。
3. 不是成员：返回 404 `ORG_NOT_FOUND`，和组织不存在时完全一样，外人无法确认某个组织 id 是否存在。是成员但角色不够：返回 403 `INSUFFICIENT_ROLE`。
4. 角色每次请求都从 `membership` 表查，不缓存在 token 里。改了角色或被移出组织，下一个请求立刻生效。
5. 以后组织下的资源（工单等）一律按 `orgId` 查询，例如 `findByOrgIdAndId(orgId, id)`，防止拿别的组织的资源 id 越权访问（IDOR）。
6. `TenantIsolationTest` 用另一个组织的 OWNER 调用每一个 `{orgId}` 接口，要求全部 404 且数据不变；同时扫描应用里所有 `{orgId}` 接口，没登记进测试的会让测试失败。

## 理由

- 显式调用一眼能看出这个方法做了什么校验，调试和代码评审都直接；`@PreAuthorize("@x.check(#orgId)")` 把逻辑藏在字符串表达式里，拼错了编译器也发现不了。
- `requireRole` 返回 `Membership`，后续业务逻辑（比如"客户只能看自己的工单"）可以直接用其中的角色，不用再查一次。
- 组织 id 在 URL 里，每个请求都是自包含的，不需要服务端记住"当前组织"，前端切换组织只是换个 URL。

## 代价

- 每个新的 Service 方法都要记得调用校验。用 `TenantIsolationTest` 的接口清单检查来兜底：新增 `{orgId}` 接口但没登记，CI 会红。
- 每个请求多一次按主键查 `membership` 的查询，成本很低。

## 未选方案

- `@PreAuthorize` + 方法级安全：可以做，但对这个规模没有明显好处，理由见上。
- `ThreadLocal` 的 `TenantContext`：由过滤器解析 orgId 放进去，Service 隐式读取。隐式依赖让单元测试和异步任务更容易出错，而 orgId 已经在方法参数里了。
- PostgreSQL 行级安全（RLS）：数据库层兜底，最安全，但需要每个连接设置会话变量，和连接池、JPA 配合有额外复杂度。放到阶段 5 作为加分项。
