# ADR 0001：核心实体主键使用 UUIDv7

- 状态：已采纳
- 日期：2026-10-06

## 背景

TriageDeck 是多租户 B2B SaaS 工单系统（Java 21 + Spring Boot 4.1 + Spring Data JPA + PostgreSQL 18）。组织、用户、工单的 id 会出现在 API 和 URL 中。候选方案：

- A：UUIDv7 作唯一主键，由数据库 `uuidv7()` 生成
- B：自增 bigint
- C：内部 bigint 主键 + 对外暴露的 UUID 列

## 决策

采用 A。组织、用户、工单使用 UUIDv7 作唯一主键，默认值 `DEFAULT uuidv7()` 写在 Flyway 迁移中；API 和 URL 直接使用该 UUID。工单另设组织内展示编号 `number`（`UNIQUE(org_id, number)`），供人阅读和口头沟通。纯关联表（如 Membership）使用联合主键 `(user_id, org_id)`。

## 理由

1. 对外 id 不可顺序枚举。
2. 不泄露客户数和增长速度（"德国坦克问题"）。对 B2B SaaS 这是合理的顾虑，但不是硬性要求。
3. 只维护一种标识，数据库、API、URL 一致。
4. UUIDv7 按时间递增，插入集中在 B-tree 尾部附近，避免了 UUIDv4 的随机插入问题。

## 代价

- 键 16 字节（bigint 8 字节），索引和外键更宽。
- UUIDv7 包含大致的创建时间（前 48 位是毫秒时间戳），因此保留独立的 `created_at` 列。
- 由数据库生成主键时，Hibernate 无法批量插入；工单为逐条交互式创建，影响可接受。
- 不便口述，由工单编号弥补。

## 未选方案

- B（自增 bigint）：简单、紧凑、便于调试，但对外暴露连续 id，可被枚举并泄露增长趋势。
- C（bigint + 对外 UUID）：兼顾两者，但需维护两套标识；目前没有大量内部关联或高吞吐批量写入的需求，不值得付出这个复杂度。若将来出现这类需求，再重新评估。

## 重要约束

主键类型不能替代授权。每个接口都必须：

1. 通过 Membership 校验当前用户属于所选组织（不信任请求中的 orgId）；
2. 按可信的租户上下文查询，如 `findByOrgIdAndId(orgId, id)`；
3. 校验具体操作权限；
4. 校验关联写入（如被分派人属于同一组织）。

用集成测试证明：租户 A 的用户使用租户 B 的真实 UUID 读取或修改资源，均被拒绝。

## JPA 映射

```java
@Id
@org.hibernate.annotations.Generated
@Column(name = "id", nullable = false, updatable = false)
private UUID id;
```

不使用 `GenerationType.UUID`（Java 侧生成 v4）。若将来需要批量插入或在 INSERT 前获得 id，可改为 `@UuidGenerator(style = UuidGenerator.Style.VERSION_7)` 在应用侧生成。
